# 013 · 총괄센터 (Studio HQ) — 스토어 콘솔을 손으로 열어 보던 걸 그만두기 위한 대시보드

> 앱 스토어 두 곳, 앱 다섯 개. 매번 콘솔을 하나씩 열어 다운로드·매출·평점을 확인하던 걸
> 로컬 수집기 + 정적 대시보드로 대체했다.

- **분야:** 내부 도구 · 데이터 수집 / 대시보드
- **위험도:** Tier 2 (재무 데이터·특권 API 키를 다룬다)
- **상태:** MVP 가동 중 (매일 자동 수집)

## 왜 만들었나

앱이 다섯 개로 늘면서 "무엇이 팔리는지 모른 채 다음 앱을 정한다"는 문제가 분명해졌다.
App Store Connect와 Google Play Console을 앱마다, 스토어마다 따로 열어야 했고
통화·기간 기준도 서로 달라 비교가 안 됐다. 지표를 기록해 둔 곳은 없었다.

다음 앱을 뭘 만들지, 마케팅에 시간을 더 쓸지를 감이 아니라 숫자로 정하고 싶었다.
서드파티 대시보드는 구독료가 들고 재무 데이터를 외부로 보내야 해서 제외했다.

## 무엇을 만들었나

- **Python 수집기 5종** — App Store Connect API(판매 리포트·리뷰)와 Google Play
  (Reporting API로 크래시·ANR, Cloud Storage 월간 CSV로 설치·평점·매출)를 각각 읽는다.
- **로컬 SQLite** — 수집한 걸 그대로 쌓는다. 외부 서버 없음.
- **정적 HTML 대시보드** — 서버 없이 파일을 직접 연다. 인라인 SVG로 그래프를 그린다.
- **launchd로 매일 자동 실행** — 맥이 꺼져 있던 시간대는 다음 예정 시각에 건너뛰어 실행되고,
  각 수집기가 "마지막 성공 이후 ~ 오늘"을 채우는 방식이라 결측이 자동으로 메워진다.
- 재무 데이터와 API 키를 다루기 때문에 Tier 2로 분류하고 보안 리뷰를 필수로 뒀다.

## 만드는 과정

**MVP는 하루 만에 구조를 잡았다.** 수집기·스키마·대시보드·launchd 스크립트를 만들고
파서 단위 테스트를 붙였다. 그다음 보안 리뷰를 돌렸는데 즉시 막을 문제(blocker)는
없었고, 비차단 권고 몇 개만 나왔다 — 이후 실제로 API를 붙이며 나온 문제들이 더 컸다.

- **매출 리포트를 받으려면 별도 키 역할이 필요했다.** 앱 관리용 API 키로는 판매 리포트
  엔드포인트에 접근할 수 없었다. "판매 및 보고" 역할을 가진 키를 따로 만들고서야 풀렸다.
- **raw 다운로드에서 인증 헤더가 빠져 401, `Accept` 헤더가 없어 406**이 났다. 리포트
  목록 API와 실제 파일을 받는 raw 다운로드가 별개의 요청 규약을 요구했다.
- **가장 컸던 버그: 인앱 구매 매출이 통째로 빠지고 있었다.** 판매 리포트의 각 행은
  상품 식별자로 식별되는데, 인앱 구매 행은 앱 자체의 식별자와 다른 식별자를 쓴다.
  그걸 앱에 매칭하는 로직이 없어 인앱 매출이 전부 누락된 채 "매출 0"으로 보였다.
  Parent Identifier(부모 SKU)로 귀속시키자 그제야 실제 수치가 잡혔다.
- **테스트가 운영 DB를 오염시키고 있었다.** 파서 테스트가 실제 SQLite 파일에 쓰고
  있었던 걸 뒤늦게 발견하고, 테스트는 인메모리 DB로 격리했다.
- **Play는 애초에 "어제 설치 수"를 볼 방법이 없다.** 크래시·ANR은 Reporting API로
  매일 받을 수 있지만, 설치·평점·매출은 Play Console이 월 1회 Cloud Storage에 떨궈주는
  CSV가 유일한 공식 경로다. 데이터가 실제로 반영되기까지 며칠, 월간 리포트 게시까지
  합치면 최대 몇 주가 밀릴 수 있다. 그래서 대시보드는 스토어별로 "기준 시점"을
  따로 표시하게 만들었다 — 안 그러면 iOS·Android 수치를 같은 날짜인 것처럼 오독한다.

## 배운 점

- **"매출 0"은 버그일 확률이 코드가 맞을 확률보다 높다.** 인앱 구매 누락은 조용히
  가장 중요한 숫자를 틀리게 만드는 버그였다. 콘솔에 표시되는 값과 대조하지 않았다면
  한동안 몰랐을 것이다. 파이프라인을 만들고 나서 제일 먼저 할 일은 신뢰가 아니라 대조다.
- **API 키에는 역할이 있고, 최소 권한은 결국 키가 여러 개라는 뜻이다.** 하나의 키로
  다 되길 기대하면 안 된다. 필요한 권한 단위로 키를 쪼개는 게 기본값이어야 한다.
- **테스트는 운영 데이터를 건드리면 안 된다.** 당연한 원칙인데도 초기 구현에서
  깨졌다. 스토리지 계층에 경로를 주입할 수 있게 하고, 테스트는 인메모리로 고정했다.
- **지표 도구를 만들고 나서 처음 나오는 결과물은 보통 인사이트가 아니라
  데이터 품질 버그 목록이다.** 수집·집계 로직을 다 짜고 나서야 "이 숫자가 맞는가"를
  검증할 수 있게 되고, 그 검증에서 진짜 문제가 드러났다.
- **스토어마다 데이터 신선도가 다르면, 대시보드는 그 차이를 숨기면 안 된다.** 같은
  화면에 나란히 놓인 숫자라도 "언제 기준인가"가 다르면 비교 자체가 오독이다.
